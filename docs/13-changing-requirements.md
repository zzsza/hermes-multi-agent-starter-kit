# 요구사항을 바꾸는 방법

역할과 업무 판단 기준은 문서, 연결과 권한은 설정, 강제 제한은 코드에 나눠 두었습니다. 운영자가 Slack에서 한 번 말한 내용만으로 영구 운영 규칙과 권한을 바꾸지는 않습니다. 원하는 변경을 이 자료 폴더에 반영한 뒤 실제 프로필에 적용합니다.

## 무엇을 어디서 바꾸나

| 변경할 내용 | 수정할 파일 | 코드 수정 필요 |
|---|---|---|
| A의 역할, 말투, CX 확인 기준 | `templates/main/SOUL.md` | 보통 없음 |
| CX의 역할, A에게 보고할 기준 | `templates/cx/SOUL.md` | 보통 없음 |
| 업무별 입력, 출력 형식과 금지 사항 | 받은 업무 자료로 작성한 프로필별 스킬 | 기존 도구 범위라면 보통 없음 |
| 사람 조율 담당자 | 실제 main `.env`의 `HUMAN_REVIEW_USER_ID` | 없음, main 허용 목록과 채널 참여도 확인 |
| 요청할 팀원 | 실제 프로필 `.env`의 `SLACK_ALLOWED_USERS` | 없음, 관리자 목록과 구분 |
| 사용 채널 | 두 `.env`의 채널 허용 목록과 home channel | 없음, 두 봇 모두 초대 필요 |
| 모델과 응답 제한 | `templates/main/config.yaml`, `templates/cx/config.yaml` | 지원 모델과 설정 확인 필요 |
| CX 응답 대기 시간, 강제 왕복 차단 | `plugins/cx-thread-bridge/__init__.py` | 필요, 관련 테스트도 수정 |
| 마케팅 직원 추가와 새 전달 경로 | 새 프로필, 앱, SOUL과 연결 코드 | 현재 버전에서는 필요 |
| 외부 문의 접수와 주문 이벤트 | 해당 서비스의 이벤트 연결 | 현재 버전에서는 필요 |

직원 추가가 YAML에 이름 하나 넣으면 끝나는 범용 조직 엔진은 아직 아닙니다. 현재 필요한 A와 CX의 두 경로만 구현했습니다. 역할과 기준을 바꾸는 데에는 엔진을 새로 만들 필요가 없습니다.

## 변경 요청을 적는 양식

```text
변경 목적:
현재 동작:
원하는 동작:
적용할 직원과 상황:
필요한 자료와 근거:
사람에게 넘길 조건:
실행하면 안 되는 행동:
예시 입력과 기대 결과 2~3개:
```

예를 들어 “정책이 없다는 이유만으로 전부 A에게 보내지 말고, 체크리스트 작성은 CX가 직접 답하고 최종 결정을 요구할 때만 A에게 보내기”처럼 경계를 구체적으로 적습니다. 현재 SOUL에도 이 구분이 들어 있습니다.

## 적용 순서

1. 어떤 역할과 동작이 바뀌는지 위 표에서 찾습니다.
2. 이 자료 폴더의 해당 원본을 수정합니다. 인증값을 넣지 않습니다.
3. 문서와 설정 검사, 관련된 코드 테스트를 실행합니다.
4. 기존 프로필 변경과 백업을 비교한 뒤 설치 가이드의 apply_profiles로 적용합니다.
5. 두 프로필을 재시작하고 작은 가상 사례로 해당 분기만 확인합니다.
6. 기대 동작, 실제 결과와 테스트 스레드 링크를 남깁니다.

```sh
~/.hermes/hermes-agent/venv/bin/python checks/validate_templates.py
~/.hermes/hermes-agent/venv/bin/python -m unittest discover -s checks -p 'test_*.py'
hermes -p cx gateway restart
hermes -p main gateway restart
```

위 재시작 명령만으로 이 폴더의 템플릿이 런타임에 복사되지는 않습니다. 먼저 [설치 가이드](08-reproduce-a-cx.md)의 apply_profiles를 실행하거나 변경 파일을 해당 실제 프로필에 정확히 반영해야 합니다.

apply_profiles는 config와 SOUL을 백업하고 이 폴더 내용으로 교체합니다. 허용 사용자는 지정한 운영자와 상대 봇, 조율 담당자는 지정한 운영자로 재설정합니다. 나중에 추가한 팀원과 담당자 변경이 있으면 해당 운영 변경도 다시 반영해야 합니다. 기존 Slack 토큰과 OAuth는 프로필별로 보존합니다.

## 문서 변경으로 풀 수 없는 제한

SOUL에 “CX 보고를 다시 CX에 보내도 된다”고 써도 도구가 발신자를 확인해 거부합니다. A가 맡긴 작업을 CX가 다시 A에게 보고하는 것도 코드에서 막습니다. 허용 채널과 요청 스레드, 고정 수신자, 중복 방지 역시 도구가 제한합니다.

이 경계를 바꾸려면 코드와 검증을 함께 바꿔야 합니다. 외부 발송과 데이터 수정 도구는 현재 없으므로, “승인하면 실행”이라는 문장을 추가해도 실제 실행 기능이 생기지 않습니다. 새 도구와 승인 절차가 필요합니다.

## 다른 컴퓨터로 옮길 때

수정한 자료 폴더를 함께 옮깁니다. 해당 Mac에서 인증과 Slack 토큰을 준비한 뒤 같은 템플릿, 플러그인과 스킬을 적용합니다. 런타임 프로필에만 수정해 두면 다음 Mac에서는 그 변경이 재현되지 않습니다.

설치와 이전은 [재현 가이드](08-reproduce-a-cx.md), 운영은 [일상 관리](../OPERATIONS.md), 실제 동작 범위는 [CX 시작 조율](12-cx-first-coordination.md)을 참고합니다.
