# 상황별 사용 사례와 사람 조율

기본 흐름은 `사람 → A → 필요하면 CX → A의 정리`입니다. A와 CX가 결론을 낼 근거가 없으면 `A → 지정 담당자 태그 → 사람의 스레드 답변 → A가 이어서 정리`로 전환합니다. 서로 계속 설득하는 봇 대화는 하지 않습니다.

사람 태그는 현재 고정 담당자 한 명에게만 가능합니다. 팀별 담당자 자동 선택, 부재중 대체 담당자, 시간 경과 후 반복 알림은 아직 구현하지 않았습니다.

CX에게 직접 들어온 요청에서도 조율이 필요하면 CX가 먼저 A에게 보고할 수 있습니다. 이 경로의 실제 시험 결과와 제한은 [CX 시작 조율](12-cx-first-coordination.md)을 참고합니다.

## 어떤 상황에 어떻게 쓰나

| 상황 | 요청 예시 | 기대 동작 | 확인 범위 |
|---|---|---|---|
| 일반 정리 | `@Hermes A 회의 메모를 할 일 3개로 정리해줘` | A가 직접 정리 | 일반 요청 분기를 실제 Slack에서 확인 |
| 고객 응대 준비 | `@Hermes A 배송 지연 환불 문의에서 확인할 정보를 정리해줘` | A가 CX에게 확인한 뒤 답변 | 실제 A와 별도 CX의 호출과 회신 확인 |
| 같은 건에 추가 질문 | 스레드에서 `고객에게 물을 질문 2개만 줘` | 기존 CX 의견으로 답할 수 있으면 재호출 없이 A가 정리 | 실제 Slack에서 확인 |
| 새로운 사실 | 스레드에서 `이미 상품을 받았다는 정보가 추가됐어` | 필요하면 새 CX 확인, 같은 스레드에서 정리 | 실제 두 번째 CX 확인 성공 |
| 정책이 없어 확답 불가 | `전액 환불을 확정할지 결정해야 하는데 승인 기준이 없어` | A가 미확정 사항을 정리해 담당자를 태그하고 판단 대기 | 실제 Slack에서 CX 확인 후 담당자 태그와 후속 대화 확인 |
| 내부 자료가 충돌 | `상담 기록에는 환불 승인, 정산 기록에는 보류라고 되어 있어` | CX의 확인 의견을 받고 최종 근거를 사람이 선택하도록 요청 | 가상 충돌 사례로 실제 CX 확인과 담당자 태그 확인, 실제 업무 자료로는 미검증 |
| 고객에게 발송 전 확인 | `이 답변을 고객에게 보내도 될지 승인받아줘` | 같은 스레드에 발송할 초안과 승인 질문을 남기고 담당자 태그 | 승인 요청 분기 구현, 실제 고객 발송 기능 없음 |
| CX가 답하지 않음 | A의 CX 확인 후 120초 안에 완성된 결과가 없음 | 재전송 없이 지정 담당자 태그 시도 | 자동 처리의 단위 테스트 통과, 실제 장애 유발 시험은 하지 않음 |
| 처리 범위 밖 | `지금 결제 취소와 CRM 수정을 실행해줘` | 실행 불가 범위와 필요한 사람 처리를 정리, 필요하면 태그 | 도구 자체를 제공하지 않음, 실제 시스템 변경 없음 |
| 구독 오류 | Codex 인증 또는 한도 오류 | API로 전환하지 않음 | fallback 비활성 확인, 실제 한도 소진 시험 없음 |

## 사람이 받게 되는 알림

태그 메시지는 같은 요청 스레드에 남습니다. 다음은 형식 설명용 예시이며 실제 업무 정책이 아닙니다.

```text
@담당자 확인이 필요합니다: 정책 또는 근거 부족
고객은 배송 지연으로 전액 환불을 요청했습니다.
CX 확인 의견은 정책 확인 전 확답을 보류하자는 것입니다.
확인할 사항: 이 주문에 적용할 환불 기준과 최종 승인자를 알려주세요.
이 스레드에 판단 또는 추가 정보를 남겨주세요.
확인 전에는 해당 작업을 진행하지 않겠습니다.
```

사람이 할 일은 봇끼리의 대화를 재중계하는 것이 아니라 **막힌 결정 한 가지를 해결할 근거와 판단을 주는 것**입니다. “알아서 해” 대신 적용할 정책, 우선할 원본 자료, 승인 또는 보류 여부를 적습니다.

```text
이번 건은 판단을 보류해 주세요.
먼저 주문 시각, 실제 배송 상태, 적용 약관의 버전을 확인해 주세요.
고객 발송과 환불 실행은 제가 직접 하겠습니다.
```

이 답변은 main 허용 목록에 등록된 담당자가 같은 스레드에 남겨야 합니다. 다른 사람이 태그되었다는 이유만으로 봇 사용 권한을 얻는 것은 아닙니다.

## 봇끼리 의견이 달라질 때

현재는 A가 CX에게 한 번 묻고 결과를 받습니다. A는 CX의 결론을 그대로 승인으로 취급하지 않습니다. 고객사 근거와 충돌하거나 판단이 필요한 경우 두 주장의 근거와 질문을 정리해 사람에게 넘깁니다. 같은 처리에서 CX를 재귀적으로 부르거나 여러 에이전트를 새로 생성하지 않습니다.

문제가 해결되기 전에는 해당 결정을 진행하지 않습니다. 담당자의 후속 답변을 받으면 새 A 처리에서 내용을 반영할 수 있습니다. 현재 승인 답글은 환불이나 발송을 자동 실행하는 버튼이 아닙니다. 해당 실행 도구가 없으므로 최종 처리는 사람이 합니다.

## 알림의 한계

같은 A 처리 안에서는 담당자 태그를 한 번만 보내도록 중복을 막습니다. 새 후속 요청은 새 처리이며, 다시 판단이 막히면 새 확인 요청이 생길 수 있습니다. 같은 사안의 영구적인 승인 티켓과 해결 상태를 관리하는 기능은 아직 없습니다.

Slack 자체가 끊겼거나 A가 모델 응답을 만들기 전 인증 오류로 중단되면 담당자 태그도 보장할 수 없습니다. 외부 장애 감시와 별도 연락망은 아직 연결하지 않았습니다. 프로세스 재시작을 넘어서는 영구적인 중복 방지, 자동 재촉 알림도 범위에 없습니다.

정기 보고, 새 주문 같은 외부 이벤트, 팀별 승인자 배정은 추후 확장 사례입니다. 현재 등록한 cron과 외부 이벤트 트리거는 없으며 채널 멘션과 A가 참여 중인 스레드 후속 답변으로 시작합니다.
