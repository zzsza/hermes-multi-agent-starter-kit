# CX가 먼저 A에게 조율을 요청하는 구조

2026-10-26 추가 구현입니다. 이전 A 시작 경로를 유지하면서 CX가 직접 받은 사람 요청을 검토하다 A에게 먼저 보고하는 경로를 추가했습니다.

```text
사람이 CX에게 요청
        ↓
CX가 자기 업무 검토
        ↓
조율 필요 판단
        ↓
같은 스레드에서 A에게 조율 보고
        ↓
A가 보고 검토
        ├─ 직접 정리
        └─ 담당자 판단이 필요하면 사람 태그
```

이벤트의 시작은 현재 지정 채널에서의 실제 CX 멘션입니다. 새 문의 접수 웹훅, 주기적 이상 징후 감시, 채널의 모든 메시지를 수집하는 기능을 추가한 것은 아닙니다. 외부 이벤트를 연결하면 같은 보고 구조를 활용할 수 있지만 아직 등록된 외부 이벤트는 없습니다.

## 역할별 도구

같은 `cx-thread-bridge` 플러그인을 두 프로필에 설치하고, 프로필별 환경과 도구 묶음으로 역할을 나눕니다.

| 프로필 | 도구 | 하는 일 |
|---|---|---|
| main | consult_cx | 사람이 A에게 요청한 업무에서 실제 CX에게 확인하고 완성된 답을 기다림 |
| main | request_human_review | 현재 스레드에서 고정 담당자에게 판단 요청 |
| cx | report_to_main | 사람이 CX에게 요청한 업무에서 조율할 내용을 A에게 보고, 회신 대기는 하지 않음 |

CX `.env`에는 `MAIN_AGENT_USER_ID`를 설정합니다. main의 허용 목록에 운영자와 CX Member ID, cx의 허용 목록에 운영자와 A Member ID를 넣습니다. 두 봇은 멘션한 봇 메시지만 받고 다른 봇 전체를 허용하지 않습니다. DM과 채널의 관리자 명령 권한은 계속 운영자 한 명입니다.

CX는 `cx_report`, A는 `cx_consult` 도구 묶음을 사용합니다. 같은 코드 파일을 설치했다고 두 프로필이 같은 권한을 받지는 않습니다. CX에는 사람 태그와 CX 호출 도구를 등록하지 않습니다.

## 언제 CX가 보고하나

- 고객 응대 자료와 다른 팀의 자료가 충돌해 기준 선택이 필요한 경우.
- 고객 문의에서 광고 문구의 오류 가능성을 발견해 다른 업무의 검토가 필요한 경우.
- 정책이 없어 고객에게 확답할 수 없고 승인자의 판단이 필요한 경우.
- CX 권한으로 처리할 수 없는 작업을 요청받은 경우.

단순한 질문이나 확인 항목 정리는 CX가 직접 답합니다. 보고에는 확인한 사실, 미확인 사항, CX의 검토 의견과 A가 결정할 질문을 담습니다. 사실을 수집하는 외부 도구가 없으므로 입력받지 않은 주문 상태와 정책을 조회했다고 말해서는 안 됩니다.

## 직접 해볼 요청

운영자가 테스트 채널에서 CX만 실제 멘션합니다. A에게 보내라고 명시하지 않고도 CX가 조율 필요성을 판단하는지 확인합니다.

```text
@Hermes CX 가상 주문의 상담 기록에는 환불 승인, 정산 기록에는 보류라고 적혀 있어.
작성 시각과 권한은 같고 우선 기준은 없어. 어느 쪽을 기준으로 삼아야 할지 결정이 필요해.
추측하지 말고 확인해줘. 실제 환불, 데이터 수정과 고객 발송은 하지 마.
```

기대 흐름은 CX의 A 멘션 보고, A의 직접 검토, 근거가 없으면 A의 담당자 태그입니다. 같은 스레드에 남고 CX를 다시 부르는 질문은 없어야 합니다. 담당자는 허용 계정으로 그 스레드에 판단을 남깁니다.

## 왕복 루프를 막는 경계

이 버전은 봇끼리 자유롭게 반복 대화하는 구조가 아닙니다. 다음 두 경로만 제공합니다.

1. 사람 → A → CX 확인 결과 → 원래 A 실행의 최종 답변.
2. 사람 → CX → A 조율 보고 → A의 정리 또는 사람 판단 요청.

A가 요청한 CX 작업에서는 report_to_main이 발신 요청자 A를 확인해 거부합니다. CX가 보낸 보고를 처리하는 A 실행에서는 consult_cx가 발신 요청자 CX를 확인해 거부합니다. SOUL의 말투 지시만으로 제어하지 않고 도구 실행 단계에서 막습니다. 사람이 새로운 정보를 주면 새 처리에서 재검토할 수 있습니다.

CX 보고는 한 처리에 한 번이며 전송 결과가 불명확하면 자동 재전송하지 않습니다. 중복 방지는 프로세스 메모리의 10분 캐시입니다. 재시작을 넘어서는 영구 작업 큐와 정확히 한 번 처리 보장은 아닙니다.

마케팅 직원과 다른 부서는 아직 만들지 않았습니다. A는 존재하지 않는 직원에게 배정했다고 말하지 않고 필요한 협업을 사람에게 요청합니다. 이후 실제 직원과 업무 프로세스를 추가할 때 보고 유형과 허용 경로를 확장합니다.

## 설치와 검증

[최신 설치 가이드](08-reproduce-a-cx.md)의 apply_profiles 명령을 실행하고 두 게이트웨이를 재시작합니다. 기존 두 프로필의 인증은 유지합니다. API fallback은 계속 비활성입니다. 새 구성은 기존 역할 파일과 허용 목록을 교체하므로 수동 운영 변경이 있다면 적용 전 백업과 비교합니다.

15개 단위 테스트가 통과했습니다. 추가 검사는 CX의 고정 A 보고, 현재 스레드 제한, 임의 멘션 escape, 중복 전송 방지, 양방향 되돌리기 거부와 전송 오류 처리입니다. 실제 Slack 결과는 [최신 검증 기록](10-live-verification.md)에 따로 기록합니다.
