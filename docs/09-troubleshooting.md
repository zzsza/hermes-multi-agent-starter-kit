# 시행착오와 해결 기록

작성일: 2026-10-26. 이전 개발에서 관측한 기술적 문제와 해결을 개인 정보 없이 정리했습니다. 새 대상의 계정과 설치 상태는 별도로 질문하고 확인합니다.

## 구현 기준

A와 CX의 두 경로를 사용하고 재귀적인 작업 위임을 차단합니다. API fallback은 비활성입니다. 새 설치에서 과거 환경과 같은 계정이나 채널을 가정하지 않습니다.

## 설치와 인증

| 관측한 문제 | 원인과 해결 |
|---|---|
| 기본 Python은 3.10.4인데 Hermes는 3.11.13 출력 | Hermes 전용 가상환경을 사용 중이었습니다. 작업과 테스트는 전용 Python으로 실행했습니다. |
| Slack 모듈 미설치 | `slack_bolt`, `slack_sdk`가 없었습니다. 설치 소스 pyproject의 버전으로 두 패키지를 추가했습니다. |
| `--clone`으로 OAuth까지 복제될 것으로 기대 | 실제 `_CLONE_CONFIG_FILES`에 auth.json이 없습니다. 구성 복제와 인증 복제를 구분했습니다. |
| 같은 구독 계정인데 로그인 두 번 필요 | 추가 구독을 사는 것이 아니라 프로필별 OAuth 세션을 발급했습니다. 복제 토큰의 refresh 충돌은 아직 시험하지 않았습니다. |
| 기본 프로필을 바꾸면 개인 설정 손상 가능 | 기존 default를 보존하고 main과 cx를 새로 만들었습니다. 모든 명령에 -p를 명시했습니다. |
| Docker CLI는 있는데 daemon 연결 실패 | 현재 파일럿은 터미널 도구를 제공하지 않으므로 텍스트 통신 시험은 가능했습니다. 컨테이너 격리 성공으로 기록하지 않았습니다. |

## Slack UI와 비밀값

매니페스트 생성은 공식 CLI를 사용했습니다. 설치 화면은 이전 문서의 “From an app manifest” 단일 버튼 대신 생성 방식 라디오 선택 후 Continue 형태였습니다. 화면이 다르면 현재 UI를 읽고 진행합니다.

CodeMirror 편집기에 `fill()`을 사용했을 때 JSON이 중복 삽입되어 오류가 났습니다. 전체 선택, 삭제 후 입력하는 방식으로 고쳤고, 오류 표시가 사라지고 Next가 활성화된 뒤에만 진행했습니다. 생성과 설치를 한 번 실행한 뒤 상태를 확인하며, 응답이 늦다는 이유로 Create를 반복 누르지 않습니다.

Slack 앱의 기본 정보 화면에도 Verification Token 같은 민감한 값이 있을 수 있습니다. 기본 정보 화면의 전체 상태를 그대로 도구 출력에 남기지 않습니다. token, secret과 password 필드를 가려 읽고 비밀값은 운영자가 실제 프로필 .env에 직접 입력합니다.

비밀값이 노출되면 해당 값의 재발급과 기존 값 무효화를 확인합니다. 재발급 중 미활성 후보도 외부 출력에 남기지 않습니다. Slack이 비밀번호 재확인을 요구하면 사용자가 직접 입력하며 비밀번호를 채팅으로 받지 않습니다. 토큰 종류 몇 개를 정규식으로 가리는 것만으로 모든 민감한 필드를 보호했다고 가정하지 않습니다.

## API와 스레드 처리

`chat.getPermalink`에 잘못된 `conversation_id` 인자를 넣어 `invalid_arguments`가 났습니다. 공식 API에서 필요한 키는 `channel`, `message_ts`임을 확인해 수정했습니다. 오류가 난 조회는 메시지 전송이나 중복 생성으로 이어지지 않았습니다.

A의 Slack bot token으로 `conversations.replies`를 호출해 실제 테스트 스레드를 읽을 수 있음을 확인했습니다. 사용자의 브라우저 세션만 읽을 수 있는 기능으로 착각하지 않도록, 런타임 봇 토큰으로도 별도 확인했습니다.

처음 질문을 HTML escape할 때 작은따옴표까지 인코딩해 Slack 원문에 불필요한 엔티티가 보였습니다. `quote=False`로 바꿨습니다. `<@...>`와 채널 전체 멘션은 계속 escape해, 모델이 질문 안에 쓴 문자열이 다른 사람을 태그하지 못하도록 했습니다. 이 동작은 테스트에 포함했습니다.

## 두 에이전트 연결에서 중요한 점

- 봇 메시지는 기본 무시라 A가 CX를 멘션해도 설정 없이는 작동하지 않습니다. A 시작 경로는 CX가 A의 멘션을, CX 시작 경로는 A가 CX의 멘션을 받도록 각각 허용합니다. 사용자 allowlist에도 상대 봇 Member ID가 필요합니다.
- 두 봇이 모두 스레드 후속 답글을 자동 수신하면 사람의 답글에 둘 다 반응할 수 있습니다. CX는 strict mention, A는 일반 스레드 후속 수신으로 구분했습니다.
- 일반적인 A 시작 확인에서 A는 CX 답글을 새 대화로 다시 받지 않습니다. 전용 도구가 현재 확인번호의 결과를 읽어 원래 A 실행에 돌려줍니다. 이 때문에 A와 CX가 서로 재호출하는 루프를 만들지 않습니다.
- 단순히 CX 말투를 흉내 낸 A의 출력으로 위임 성공을 판정하지 않았습니다. Slack에서 서로 다른 실제 bot user ID의 질문과 답변을 확인했습니다.
- CX가 긴 답을 쓰는 중간 내용을 완료로 취급하면 안 됩니다. 같은 확인번호의 시작과 완료 표시가 모두 있고, CX user ID와 bot ID가 맞는 답만 사용합니다.
- 한 번의 처리에서 CX 호출은 한 번입니다. 재시도와 중복 태그를 줄이기 위한 기록은 프로세스 내부 10분 캐시이며, 서비스 재시작 뒤에도 유지되는 영구 작업 큐는 아닙니다.
- 초기 실제 CS 시험은 A의 질문부터 CX의 긴 답과 A 최종 정리까지 수십 초가 걸렸습니다. 짧은 일반 계산과 같은 속도로 끝난다고 안내하지 않습니다.

게이트웨이 재시작은 기본적으로 home channel에 알림을 보낼 수 있습니다. 사용자 채널의 불필요한 상단 알림을 줄이기 위해 현재 양식에 `platforms.slack.gateway_restart_notification: false`를 넣었습니다. 진행 중 작업 중단에 대한 해당 스레드 안내는 별개입니다.

## 권한과 사람 확인

대화 허용 사용자라고 해서 설정 변경 명령까지 허용할 필요는 없습니다. 설치 소스의 `gateway/slash_access.py`에서 DM과 그룹의 관리자 목록이 별도임을 확인했습니다. 두 범위 모두 운영자를 관리자로 지정하고, 일반 사용자에게는 help와 whoami만 허용합니다.

정책 부족과 승인 필요는 대화 모델이 판단해 담당자 태그 도구를 부릅니다. CX timeout과 전송 또는 읽기 실패는 전용 도구가 담당자 확인 요청을 자동으로 시도합니다. Slack 자체가 불통이면 그 태그도 전송하지 못할 수 있으므로 실패를 성공으로 표현하지 않습니다.

설정 검사 도중 새 문서가 아직 작성되지 않아 링크 검사가 실패한 적이 있습니다. 참조 문서를 모두 작성한 뒤 최종 링크 검사를 다시 실행합니다. 코드의 네트워크 없는 테스트와 실제 Slack 시험은 별도 결과로 기록합니다.
